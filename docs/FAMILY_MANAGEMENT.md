# Device-scoped family invitations and access management

This update adds an English **Manage family** panel to an already-authorized device's monitoring page. It does not deploy the website or modify the detector, calibration, multi-person tracking, alerts or video transport.

## Architecture checked before implementation

| Existing capability | Finding / action |
| --- | --- |
| Supabase Auth | Email/password accounts and session restoration already exist. Keep them. User-editable Auth metadata supplies display names, never management authority. |
| Device bindings | `safenest_private.members(device_id,user_id)` already persists access across refresh, login and browsers. Reuse it. |
| Device list / switching | `list_my_monitors()` and existing selection lifecycle already check server-authorized devices. Add only a `can_manage` UI hint. |
| Invitations | Existing `family_invites` stores a SHA-256 hash, expiry, usage cap and enabled flag. Existing redemption has a committed per-user rate counter. Keep the same format and protections. |
| Managers | No trustworthy administrator relationship existed. Previously codes were created only by the project operator in SQL Editor. Add an explicitly granted, device-scoped manager relationship. Never auto-promote existing members. |
| Status, events, care notes | Existing checked RPCs read the current membership. Keep those access paths and stored data. |
| Presence | Existing membership trigger rotates private topic IDs and removes leases. Keep it; membership deletion invokes it. Names come from the authorized roster RPC, not socket payloads. |
| LiveKit | Existing viewer RPC and Edge Function check membership. Preserve room grants, 25-second viewer leases and the device's short-lived allowlist. Delete removed users' leases and recheck membership after acquiring the issuance lock. |

Family accounts identify relatives. A device ID identifies the monitoring installation. Room names are labels. `Person 1 / Person 2` remain temporary tracks and are unrelated to family roles.

## Supabase steps for existing installations

**Current first-manager workflow:** apply `device_claim.sql` after `family_management.sql`, then use the local one-use device claim described in [DEVICE_CLAIM.md](DEVICE_CLAIM.md). Steps 3–4 below are the trusted operator alternative for recovery or an additional manager; they are not required for a new unclaimed device. Keep existing managers unchanged.

1. Back up your current project. Apply this update's files to the existing project root while retaining `.env`, public web configuration, models, calibration and event files.
2. In your Supabase project's **SQL Editor**, run **`cloud/family_management.sql`** once. It must run after the existing migrations, in this order:

   ```text
   schema.sql
   video_schema.sql
   family_schema.sql
   website_improvements.sql
   context_monitoring.sql
   family_management.sql
   ```

   If the first five are already installed, run only the new file. Do not rerun an older `CREATE OR REPLACE` migration after the new one; it could restore an older RPC definition. The new migration itself is rerunnable and does not delete existing devices, bindings, notes or events.
3. Have the intended primary caregiver register through the existing family website and complete any email verification. As the project operator, verify their account in **Authentication → Users** and obtain its user UUID. Use the existing monitoring device UUID. Do not use a Person number, email address or room name in place of either UUID.
4. Open **`cloud/grant_device_manager.sql.example`** locally or paste its contents into SQL Editor. Replace `REPLACE_DEVICE_UUID` and `REPLACE_AUTH_USER_UUID` with the verified pair. Run it with the SQL Editor's normal project-operator privileges. This explicitly creates the binding if needed and grants management for that one device. It is idempotent. Do not commit a privately filled copy.
5. Sign in again or click **Choose home → Refresh list** in the family website. Select that device and click **Open monitoring**. The assigned account now sees **Manage family**. Regular members do not. The SQL/RPC checks enforce the same boundary even if someone manually calls the endpoint or changes the HTML.

After the device-claim migration, an authenticated account may claim a never-assigned device using a short-lived code explicitly generated by its credentialed local setup. Opening setup, first signup, display names, editable `role` metadata and family invitations grant no management rights. See DEVICE_CLAIM.md for expiry, replay and recovery protections.

Existing Realtime setup still applies: private channels and the previous authorization policies remain required; do not turn public channel access on for this feature. No new Realtime settings, keys, Edge Function deployment, Storage bucket or SDK build are required.

The website must eventually use the updated `web/` files to show the new panel. After completing the SQL steps and local review, you may publish `web/` using your existing Vercel process. This delivery has not deployed anything.

## Invite family members

1. Open **Manage family** for the intended device. The panel names the selected home.
2. Set **Expires in hours** (1–720, default 168 = 7 days) and **Maximum new members** (1–100, default 5).
3. Click **Create invitation**. Copy the code and share it privately with the intended relatives. The code is shown only in that creation response. It is not recoverable later.
4. The relative signs in, chooses **Add a home / device**, enters the code and clicks **Follow home**. Registration alone grants no access. After successful redemption, the binding is stored in the existing members table.
5. Refreshing, signing out and back in, or signing in from a new browser loads the user's already-bound devices from the backend. They do not redeem again. Multiple homes remain independently selectable.

Invitation plaintext is not stored in localStorage, sessionStorage, cookies or a database column. It is temporarily shown in the current DOM only; close, device switch, logout, page teardown, backgrounding the page, or a management access error clears it. **Copy code** explicitly copies to the user's clipboard; a manual-select fallback works when clipboard permission is unavailable. The clipboard or a message sent by the user is outside the app's storage and must be handled privately.

The invitation list shows all active usable invitations first, followed by recent history, up to 50 entries; old active codes cannot disappear behind newer revoked entries. It shows only metadata: creation/expiry, usage count, status and creator's safe display name. It never returns a code or hash. Losing a code means revoking that invitation and creating another. If creation times out, refresh the list first and revoke an unwanted new entry: the server may have committed even though the response was lost. There is no automatic retry that silently creates more codes.

Limits are enforced server-side: 5 creations per account per minute, at most 20 active usable invitations per device, and the existing 10 redemption attempts per account per minute. Invalid, expired, exhausted, revoked or disabled-device invitations return the same `invalid_invite` result without device details. Rate-limit denial returns `rate_limited`. An existing member redeeming a still-usable code does not spend another use; they never need that code for future logins.

## Remove access and revoke codes

- **Revoke invitation** prevents future redemption of that code. It does not remove already-bound members.
- **Remove access** removes only that member's binding to the current device. Other device bindings remain. The confirmation explicitly explains that **ALL outstanding invitations for this device are also revoked**, so the removed person cannot use an old shared code to join again. Create fresh invitations for other intended relatives if necessary. This is a binding revocation, not a permanent account ban: intentionally sharing a newly created code can grant access again.
- Existing care notes, snapshots and events are retained; the removed account is not deleted. There is no client ability to edit AI state through these controls.
- Managers cannot remove themselves or another manager through this panel. A project operator must change manager roles in SQL Editor after checking the intended account. The example file includes the command to remove management only while keeping viewing access. Grant a replacement before removing the last intended manager.
- Display names are user-chosen labels and may be duplicated; they are not verified identities. Confirm the intended person before revoking. Action target UUIDs are returned only to authorized managers, used as opaque RPC parameters and not printed in the interface; emails, keys and device tokens are never returned by the roster.

Deleting a membership directly in SQL Editor also runs the new lease/invitation cleanup and the existing Presence rotation. For full removal use DELETE on the intended membership, not an UPDATE that moves an account to another device. Manager roles have a foreign key to membership and disappear when that binding is deleted.

## What revocation guarantees

Once the revocation transaction commits, subsequent authorized RPC checks no longer allow the removed binding to read status/events/notes or the online roster, post notes, join the current private Presence topic, issue a new video lease, or renew an old lease. Device lists exclude it. The Edge Function still checks status authorization before signing a viewer token.

The UI's existing 3-second monitoring poll handles an access denial by clearing the device view, notes, events, recording/PiP and Presence and reloading authorized homes. The home chooser refreshes roughly every 15 seconds. An open management panel also rechecks through its RPC roughly every 15 seconds; removing just the manager role clears the panel while keeping ordinary device access.

Already-connected media is not an instantaneous database transaction: the existing device publisher refreshes its allowlist about every 3 seconds, keeps a 5-second permission horizon, removes disallowed viewers and stops sending if verification fails. Existing JWTs have their original short lifetime; this update does not pretend deleting a database row cryptographically cancels a token already signed. The deleted session is absent from the next device allowlist, even if that old token is presented again. In-flight responses and bytes already delivered cannot be recalled.

Presence topic rotation moves legitimate clients to a new private topic on their next heartbeat. An old cached Realtime subscription may briefly remain connected, but its payload contains only an `online` flag, not family names or monitoring information. The authoritative roster RPC denies the removed user immediately on the next request. Previously received data, clipboard contents and downloaded media cannot be erased remotely by removing a binding.

## Database design

- `safenest_private.device_managers(device_id,user_id,granted_at)`: RLS enabled, no client table privileges, membership foreign key with delete cascade. No broad policies.
- `family_invites.created_by`: nullable Auth UUID added for server-derived attribution. Existing SQL-created invitations remain valid; missing creator names use “Family member.” Raw code storage is unchanged: SHA-256 only.
- New authenticated RPCs: `list_family_access`, `create_family_invite`, `revoke_family_invite`, `revoke_family_member`. Every one calls the private manager check, which verifies Auth user availability, current membership, an enabled device and its manager relationship. Mutations recheck after a device row lock.
- Updated existing RPCs: `list_my_monitors` adds only a capability hint; `redeem_family_invite` serializes with management changes using the same device-first lock order; `video_viewer_session` checks membership after the device lock and retains existing grants, lease duration, release ownership and caps.
- A private membership-delete trigger clears the removed user's video sessions and disables device invitations. Existing Presence cleanup still runs. There is no new public enumeration route or frontend secret.
